## How a custom project works

1. Describe the workflow you want improved.
2. State whether you use desktop, TornPDA/mobile, or both.
3. Identify any Torn/API/data requirements you already know.
4. The workflow is scoped before development.
5. You receive a written Torn-cash quote with functions, exclusions, platform coverage, data behavior, support, source/exclusivity terms, and acceptance conditions.
6. Development, testing, delivery, and acceptance are handled as a versioned project.

For larger requests, the first recommendation may be a smaller reliable version rather than an oversized first build.

## Security and privacy

MM Torn Systems never asks for your Torn password. API access is limited to what the agreed feature actually needs, local browser/userscript storage is preferred when remote infrastructure is unnecessary, and complete API keys are not published or logged.

See [SECURITY.md](SECURITY.md) for the public security and data-handling promise.

## Engineering standard

Projects are built around:

- clean code rather than patch-on-patch fixes;
- bounded local state and efficient API/network behavior;
- root-cause debugging;
- explicit failure handling;
- versioned releases;
- regression validation;
- migration/backup planning when persistent data is involved;
- a 14-day defect warranty on agreed delivered behavior unless a written quote states otherwise.

New features requested after the agreed scope are quoted separately.
